## 1. CORE / Non-Bonus Requirements

All items in this section must be implemented before any Bonus work begins.

### A. Shared Care Note

**Glance / Top Card**
*Primary scoring relevance: Glanceability & Actionability*

- Fully readable and actionable in under 10 seconds
- Must display: critical risk flags, open actions (sourced from unresolved comments/assignments — not a separate system), allergies, medications, recent change, last update

**Longitudinal Timeline**
*Primary scoring relevance: Collaboration & AI Integration*

- Chronological, continuous feed of all patient context
- Entry types:
  - Patient/AI session summaries
  - AI-scribed consult notes (all 3 types)
  - Staff / Clinician manual edits
  - System-generated events (see definition in Section E)
- Each entry must carry metadata: `author_role`, `author_id`, `timestamp`, `type`, `provenance_pointer`

**Inline Collaboration**
*Primary scoring relevance: Collaboration & AI Integration*

- Threaded comments with resolve / unresolve state
- @mentions (simple string parsing)
- Assignment to a user (`assigned_to`)

**Revision History & Revert**
*Primary scoring relevance: Provenance & Trust*

- Full content snapshots stored in a Version table before each save
- "View changes since X" endpoint: `GET /timeline/:id/changes?since=<timestamp>`
- Revert to any previous version
- UI-layer diff display using an off-the-shelf library (e.g., `diff` npm package); no DB schema change required

### B. AI Scribe Integration

*Primary scoring relevance: Collaboration & AI Integration, Provenance & Trust*

Three note types, all carrying provenance:

| Type | `provenance_type` example |
|---|---|
| `ai_doctor_consult_summary` | `doctor_consult` |
| `ai_nurse_consult_summary` | `nurse_consult` |
| `ai_patient_session_summary` | `patient_session` |

- Each entry: `author_role = system`, carries `provenance_type` + `provenance_id` (e.g., `session_id`)
- Must appear as visually distinct entries from manual notes in the timeline

> **Role naming convention**: "Doctor" and "Nurse" refer exclusively to these AI Scribe interaction types. System user roles are always: **Patient / Staff / Clinician / Admin**.

### C. Role-Based Access Control (RBAC)

*Primary scoring relevance: Security & Privacy*

Enforcement is server-side only. The backend returns pre-filtered data to Patient users — never rely on the frontend to hide fields.

| Action | Patient | Staff | Clinician | Admin |
|---|---|---|---|---|
| Read patient-facing summary | ✓ | ✓ | ✓ | ✓ |
| Read full timeline | ✗ | ✓ | ✓ | ✓ |
| Read internal comments / raw AI-scribed notes | ✗ | ✓ | ✓ | ✓ |
| Write clinician section | ✗ | ✗ | ✓ | ✗ |
| Write staff notes | ✗ | ✓ | ✗ | ✗ |
| Access another clinic's patients | ✗ | ✗ | ✗ | ✗ |

Multi-clinic isolation rule (applies to all roles including Admin):
```
IF request.user.clinic_id != target_patient.clinic_id → 403
```

### D. Provenance & Trust

*Primary scoring relevance: Provenance & Trust*

**Provenance chain (canonical definition):**
```
Highlight.entry_id  →  TimelineEntry.id           (source-of-truth link)
TimelineEntry.provenance_type + provenance_id      (traces back to original session/source)
Highlight.quoted_text                              (locates the originating span via text-match)
```

Clicking a highlight:
1. Jumps to the linked `TimelineEntry`
2. Matches `quoted_text` within the source text
3. Applies a highlight (yellow) on the matched span

No offset-based tracking. Text-match via `quoted_text` is the chosen approach.

Each `Highlight` record must carry a `risk_reason` field.

**Conflict resolution rule:**
```
IF a Clinician edits a section that overlaps with AI-scribed or patient-provided content
THEN Clinician's version takes precedence
AND a system_event of type "conflict_flagged" is logged on that entry
```

### E. System-Generated Events

*Primary scoring relevance: Collaboration & AI Integration, Provenance & Trust*

Formal type definition for timeline entries generated by the system (not by a user):

```
type         = "system_event"
author_role  = "system"
author_id    = null
content      = human-readable description (e.g., "Conflict flagged for clinician review",
                                                   "Entry reverted to version N by [actor_id]")
```

This type covers: conflict flagging, version revert events, and other system actions that must appear in the audit trail.

### F. Audit Log

*Primary scoring relevance: Provenance & Trust, Security & Privacy*

A dedicated `AuditEvent` table for change tracking. Metadata only — no PHI, no raw clinical content.

**Minimum schema:**
```
AuditEvent(
  actor_id     — user who performed the action
  action       — one of: note_created | note_updated | note_reverted | conflict_flagged
  target_type  — e.g., "TimelineEntry", "Version"
  target_id    — ID of the affected record
  version_id   — (nullable) linked Version record when applicable
  created_at
)
```

RBAC denial logging is out of scope for the current prototype.

### G. Security & Privacy

*Primary scoring relevance: Security & Privacy*

**PHI Redaction — Central Gateway**

Every piece of content sent to the LLM must pass through a single `redactPHI()` function. No inline regex elsewhere.

```
Input:  John Wang, IC: S1234567A, Phone: 0912-345-678
Output: [NAME], IC: [ID_NUMBER], Phone: [PHONE]
```

Redacts: full names, IC / national ID numbers, phone numbers.

**Encryption:**

| Requirement | Brief Requirement | Prototype Implementation Decision |
|---|---|---|
| TLS in transit | Hard requirement | Local dev cert; hosting-provided TLS on deployment |
| Encryption at rest | Hard requirement | Architectural description only — not implemented in prototype code. This is a deliberate prototype scope decision, not a brief exemption. |

**Logging policy** (document in README):

| Allowed in logs | Not allowed in logs |
|---|---|
| user_id, entry_id, action, timestamp, version_id | Patient name, raw note content, AI prompt content, phone, IC/ID |

**Synthetic data only.** No real patient data at any point.

## 2. Concurrent Edit Strategy

*Required by `test_concurrent_edits.py`*

**Different-section concurrency (primary case):**
- `section_key` enum (`summary | plan | medication | staff_note`) scopes writes to non-overlapping regions
- Doctor edits `plan` while Staff edits `staff_note` concurrently → no overwrite, verified via `section_key`

**Same-section concurrency (deterministic resolution strategy):**
- **Optimistic Concurrency Control**: each `TimelineEntry` / section carries a `version_number`
- Client sends current `version_number` with every save request
- Backend: if stored `version_number` > client's `version_number` → return **409 Conflict**
- No merge logic required. Resolution: the writer with the stale version must re-fetch and retry
- Must be tested explicitly in `test_concurrent_edits.py`

## 3. SIMPLIFIED Bonus

*Bonus Nightingale Alignment: 10 pts total (combined with Data Decay)*

### Self-Learning / Highlight Importance

**Simplified multi-signal importance logic** (3 factors):
```
importance_score = highlight_count × 1.0
                 + recency_bonus        (higher score for more recent entries)
                 + risk_level_tag       (extra weight if flagged high-risk)
```

The brief specifies qualitative signals (recency, risk tags, clinical entities, unresolved tasks, learned interaction) without mandating a fixed formula. This is a deliberate simplification.

**Accept / Reject UI:**
- Two buttons per highlight suggestion: `[Accept]` and `[Reject]`
- Clicking records a feedback state only; no complex +2/-1 weighted scoring required

**Hard constraint (applies to core Highlight model, not just Bonus):**
Every `Highlight` must display a `risk_reason` and link to its provenance source via the `entry_id → provenance_type/id` chain.

**Honest disclosure required in brief:**
> "This is a simplified rule-based prioritization combining highlight frequency, recency, and explicit risk tags — not a full multi-signal learned model, prioritized to keep core requirements stable within the time budget."
